# LZ77 profitability and fast-seed experiments

These are explicit native Rust experiments. Ordinary encoder options remain
unchanged. Pixel losslessness is checked against original decoded samples,
including hidden RGB and 16-bit samples, using official `djxl`.

## Questions and implementation

1. Can cheap native token statistics avoid unproductive deep matching?
   `SourceConfig::scout` offers `Off`, `Observe` and `Route`. It uses the existing
   JXL raw literal, length and distance prices, small exact-match samples,
   sparse historical anchors and actual stream-width spatial distances.
   The raw cost model is reused by the seed only when stream populations match.
   Warm/overlapping seed partitions require their own cost population.
2. Can consecutive misses reduce search density? `SourceConfig::quick = Sparse`
   uses the existing Fast<7> matcher, increases probe spacing after misses and
   restores dense probing after a useful long match. Skipped positions remain
   literal values and update history in order. This is heuristic, not a proof
   that skipped matches are unprofitable.
3. Is a small two-key matcher cheaper? `DoubleFast` uses short3/long8 hashes,
   small fixed buckets and a small set of canonical spatial distances.
   Hash hits are verified against the complete original integer values.
   `DoubleFastSparse` combines the two experiments.
4. Can existing parsing be reused? A read-only audit found that ordinary
   HybridUint model trials already reuse the LZ command stream. Default e9's
   SymbolId and the tuned indexed Frontier route each have one DP pass.
   RangeReplay already has a bounded match replay cache. No new cross-pass
   cache is introduced in this experiment.

`Observe` records a recommendation without applying it. `Route` may keep full
search, return literals, or use the fast seed without DP. Sparse negative
evidence alone is inconclusive; insufficient/mixed evidence retains full search.
The explicit `require_global_savings=false` diagnostic override suppresses
scout routing. Quick modes replace the seed finder, including careful seeds,
but retain the final DP when requested. Shared indexed seeds are bypassed when
an explicit quick finder is selected.

Neither heuristic guarantees a non-increasing file size. Only decoded values
must remain exact. Comparisons retain size regressions instead of selecting a
smaller baseline after paying for both encodes.

## References and limits

- [Brotli sparse search](https://github.com/google/brotli/blob/master/c/enc/backward_references_inc.h):
  after sustained unsuccessful matching, its encoder reduces search density.
  We borrow the feedback idea, not Brotli symbols or its bitstream.
- [Zstd double-fast](https://github.com/facebook/zstd/blob/dev/lib/compress/zstd_double_fast.c):
  separate short and long hash entries motivate the small matcher candidate.
  Its byte hashes and format are not substituted for JXL integer tokens.
- [Brotli distance research](https://github.com/google/brotli/tree/master/research):
  useful diagnostic precedent. Distance bins here describe native token-stream
  matches, not raw RGB pixel distances. A smaller distance is not automatically
  a lower fitted entropy price.
- [Approximate LZ77 precompression](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.SEA.2026.16):
  proposes inexpensive repetitiveness estimation as a possible screening step;
  this is not evidence that its large-text pipeline suits JXL image windows.
- [String synchronizing sets](https://arxiv.org/abs/2609.30193): the large-text
  construction is not implemented here. Existing source indexes are retained.

Retaining `shared` across every refit pass is not an exact reuse optimization:
shared index construction changes tags, run/deep keys, anchors and layout,
while later source refit passes can select a different matcher. A future
RangeRefit memoization experiment must cache cost-independent discoveries only,
preserve query scheduling and update the chain on cache hits.

## Running

The development `encoder_lab` exposes `--lz-scout observe|route` and
`--lz-quick sparse|double-fast|double-fast-sparse`. These flags are not installed
CLI or Python options. They require an active LZ candidate, conflict with
`--search`/`--scan-only`, and do not change production scheduling.

```powershell
cargo build --release -p rs-jxl-cli --example encoder_lab
python -B tools/benchmark_lz77_scout.py --encoder target/release/examples/encoder_lab.exe --decoder path/to/djxl.exe --case image.png --out out/lz-scout/results.json --effort 9 --threads 8 --repeats 3
```

`--lz 0` means the source effort-dependent method, not disabled matching.
`--lz 1` explicitly selects the fast b3 parser, while `--lz 2` selects Optc8.
All comparison modes receive the same setting. Reports distinguish fixed-plan
native encoding from full production scheduler search. Native seconds exclude
process startup, input image decoding and disk I/O. Diagnostic parser durations
are elapsed per-call times, potentially overlapping across worker threads; they
must not be summed and presented as end-to-end wall time or CPU time.

The harness requires official-decoder pixel equality, validates nonzero
activation receipts, records every trial and uses temporary image outputs.
Reports refuse overwrite. A subprocess timeout is a harness failure, never a
production route-selection rule.

## Interpretation

The quick finder changes seed commands and fitted prices. The existing global
savings gate can therefore accept/reject different streams before DP. A faster
whole-image result does not, on its own, prove that the same deep search ran
faster. Even when DP runs, its cost model can differ. Output size and decoded
samples are measured independently; identical compressed bytes are not a goal.

The scout receipt's `calls`, `full_calls`, `literal_calls`, `fast_calls` and
`total_seconds` accumulate across native invocations. These are recommendations,
not necessarily applied routes: Observe never changes dispatch. `latest` is
only the most recently completed sample, including its distance bins, and must
not be presented as a whole-image distance histogram. Quick parser durations
also include allocation/output work, not solely match discovery.

The corpus is the pre-existing eight-image LZ regression set, not selected by
these results: two document/editor screenshots, RGBA illustration, game and web
screenshots, RGB photograph, 16-bit grayscale texture and grayscale-alpha icon.
Every mode is checked with official libjxl 0.12 `djxl`; no decoder is modified.

An initial one-repeat six-mode screen (`out/lz-scout-20261110/screen-e9-t8.json`)
passed all 48 original-pixel comparisons. The scout made 688 recommendations,
all `Full`: zero literal or fast routes were applied. Its accumulated probe
time was about 0.399 seconds (excludes raw histogram construction). Total native
encoding was 14.513 s baseline, 14.926 s Observe and 15.164 s Route. This is a
negative screening result, not evidence of acceleration or of good routing
accuracy. Do not loosen thresholds simply to force activation on these images.

The three quick modes showed enough promise to warrant a separate rotated
three-repeat comparison, retaining every size/time regression. Both the scout
and quick modes remain disabled in production defaults and unexposed in Python.

considering any default change. No 100/500-image or cross-platform run is claimed.

### Where the illustration acceleration comes from

A separate `RS_JXL_PROFILE=1` diagnostic run, captured through subprocess pipes
(not the PowerShell native-error pipeline), showed:

| Stage | Baseline calls / inclusive s | Sparse | DoubleFast |
| --- | ---: | ---: | ---: |
| Deep source optimal parser | 15 / 12.129 | 17 / 11.480 | 5 / 3.833 |
| Fast seed | 32 / 0.272 | replaced | replaced |
| Careful seed | 48 / 0.031 | replaced | replaced |
| Quick seed | absent | 80 / 0.175 | 80 / 0.181 |

The DP count reduction explains much of DoubleFast's illustration speedup. It is
not equivalent-work acceleration. The profile times overlap across workers and
contain instrumentation overhead; they are not substituted for benchmark times.
Sparse changes fitted prices and admission too, so it is also not a guarantee
of an identical DP search. MA code is unchanged in all these variants.

## e5 comparison and disposition

The same images were also screened at e5: four modes, one repeat, 32 exact
pixel comparisons, recorded in `out/lz-scout-20261110/screen-e5-t8.json`.
Sparse was then compared against baseline three times (48 comparisons), in
`out/lz-scout-20261110/repeat-e5-t8.json`:

| Mode | Total bytes | Weighted bpp | Native seconds | MPix/s |
| --- | ---: | ---: | ---: | ---: |
| e5 baseline | 18,359,660 | 7.366181 | 2.307 | 8.644 |
| e5 Sparse | 18,346,456 | 7.360884 | 2.349 | 8.488 |

This is -0.071919% total size but +1.84% time, not an acceleration result.
The cursor grew from 33,783 to 34,568 bytes (+2.3237%); the illustration shrank
1.3765% but took 8.95% longer. At e5, the source default fast matcher has fewer
bucket entries than the experiment's Fast<7>; this comparison changes both
candidate capacity and query density, not sparsity alone.

Disposition:

- Keep all new controls opt-in, with no production scheduling, main CLI or
  Python default change. Scout currently costs work without useful routing on
  this corpus; it is not ready for deployment.
- Sparse at e9 is the most promising follow-up, but its modest/noisy timing
  evidence and per-image regressions require a larger, diverse paired trial.
- Do not adopt DoubleFast's aggregate speedup without addressing the 1.57%
  illustration growth. A 0.25% per-image allowance would reject this case.
- Do not automatically move Sparse into lower efforts based on the e9 result.
- Do not add another index cache for the default one-pass path. Existing cache
  reuse and a future optional RangeRefit experiment are separate work.

## Verification

- 291 focused LZ77 unit tests, then two additional dispatch tests: all passed.
  The latter exercise both Literal/Fast routing and the explicit forced-acceptance
  diagnostic override, replaying original tokens and checking actual DP work.
- 29 `encoder_lab` CLI tests and nine benchmark-harness tests: passed.
- `cargo check --workspace` (including the C ABI crate), `cargo fmt --all --
  --check` and `git diff --check`: passed.
- 224 real PNG encode/official-decode comparisons: passed, including original
  hidden RGB, gray-alpha and 16-bit integer values. No generated JXL or decoded
  PNG artifacts are retained by the harness.
- Input ICC warning messages from libpng were retained. These tests check pixels,
  not metadata retention; no metadata-conformance claim is made here.
- Release executable was built before benchmarking; no compilation or other
  benchmark was run concurrently with timed trials. Additional diagnostic profile
  runs are excluded from benchmark aggregates and the 224 comparison count.
