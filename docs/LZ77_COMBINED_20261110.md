# Cost-ranked sparse double-hash follow-up

This continues the [first LZ77 experiment](LZ77_SCOUT_20261110.md). It is an
explicit native Rust experiment, not a production default or decoder change.
The existing `sparse`, `double-fast` and `double-fast-sparse` controls remain
available. Prior JPEG entropy experiments are independent and unchanged.

## New candidate

`SourceQuickMode::DoubleFastCost`, exposed by the development encoder lab as
`--lz-quick double-fast-cost`, combines:

- The two short3/long8 hash tables, with full original-value verification.
- Sparse queries after unsuccessful matching, while updating skipped history.
- The previous five spatial probes plus the first 24 native JXL spatial offsets,
  deduplicated by physical distance and priced by their canonical symbols.
- Gain ranking using existing source seed literal sums, starting-context penalty
  and static length/distance prices. This is not the final fitted ANS bit cost.
- Verified prefix choices at the source seed HybridUint(1,0,0) length-price
  interval endpoints, plus the maximal exact match. Literal prices are
  nonnegative, so the longest prefix within a constant-price interval has the
  highest local gain in that interval. This does not optimize the whole parse.
- Original careful-seed dispatch below 65,536 combined input tokens, or when
  explicitly forced. The other quick experiments retain their old behavior.

The candidate does not use filenames, image classifications or measured output
sizes as routing rules. It does not run baseline and new full encodes to select
the smaller output. There is no claim of a guaranteed non-increasing file size.

## Correctness and work bounds

Each nominee is independently extended and verified. Longest-match pruning is
not valid when a shorter match can have a higher gain. Distance-code numbers
are not monotonically ordered by price, and narrow-width aliases are always
priced through the same canonical mapping used by subsequent encoding.

If no strictly positive candidate exists, the longest legal rejected match is
returned to the original emission/rejection gate. This preserves its long-run
skip and zero-gain acceptance behavior. It also applies to ungated methods:
choosing the least-negative three-value prefix of a long zero-cost run would
repeatedly extend the same suffix, causing quadratic work. Entire zero-priced
suffixes bypass extension in gated methods. Query history is still updated in
order; no future origins enter the dictionary.

The original f32 operation order is retained for selection and emission.
Heuristic price precision is not a pixel precision change. Overlapping copies,
full-width integer values and hidden RGB remain exact.

`lz_quick.cost_ranked_calls` counts actual new-parser invocations;
`preserved_careful_calls` counts deliberate original-parser bypasses. Bypasses
are not claimed as new algorithm activation. The harness distinguishes a
`preserved-careful-bypass` result from a silently ignored option.

## Corpus and measurement

`out/lz-combined-20261110/cases24.json` contains the previous eight controls plus
16 preselected existing images, without consulting compression outcomes.
It records categories, source-manifest indices and input SHA256 identities.
The total is 47,539,775 pixels: six photos, eight screenshots, three illustrations,
sprite/flat and alpha controls, two 16-bit grayscale textures and one 16-bit
RGBA texture. This is a coverage sample, not a statistically representative
random sample. No input is resized or converted to a lower bit depth.

The initial `screen-e9-t8.json` is deliberately retained as a failed report:
all four modes rejected `Job_Simulator_screenshot_-_Kitchen_02.png` before
encoding, with `PNG sRGB conflicts with gAMA/cHRM`. The other 23 files passed
all four pixel checks. No decoder tolerance or metadata check was relaxed.
`replacement-e9-t8.json` verifies the next unused game screenshot from the
pre-existing sample manifest, `Chasing_Aurora_screenshot_10_(Chase).png`, in
all four modes. Its dimensions are the same as the rejected file.

`cases24-v2.json` explicitly records this one input-format replacement and
retains the excluded path/reason and the original manifest. The repeated
comparison uses v2. Replacement was due to shared input rejection, not size
or timing outcomes; image files themselves remain unchanged.

The comparison uses fixed native encoding plans at e9, eight threads and the
same binary, not production scheduler searches. Native time excludes input
decoding, process startup and disk I/O. Execution is serial with mode order
rotated. Every output must decode through official libjxl 0.12 `djxl` to the
original PNG values, including alpha-zero RGB and 16-bit samples. Bad size/time
results are retained. Temporary JXL and decoded PNG files are removed by the
harness; only JSON statistics are retained.

```powershell
cargo build --release -p rs-jxl-cli --example encoder_lab
python -B tools/benchmark_lz77_scout.py --encoder target/release/examples/encoder_lab.exe --decoder path/to/djxl.exe --manifest out/lz-combined-20261110/cases24-v2.json --out out/lz-combined-20261110/repeat-e9-t8.json --effort 9 --threads 8 --repeats 3 --mode baseline --mode sparse --mode double-fast-sparse --mode double-fast-cost
```

The manifest and generated reports are ignored local experiment artifacts.
All new behavior remains opt-in until size, timing and compatibility evidence
supports a separate default-policy decision.

The illustration's old combined result was 466,766 bytes (+1.658053%) and
1.506 seconds (-39.77%). The new combination reduces that growth to 0.645101%,
but gives up most of the speed gain. It still exceeds the requested 0.25%
per-image size allowance, and its baseline is already only 2.5 seconds. This
is not an acceptable automatic speed/size trade-off under the user's policy.
For the PDF, recovering 385 bytes relative to the old combination still does
not make the new mode faster than baseline.

The receipts confirm that the new mode is active on all 24 images. Summing
the first repetition per image gives 754 cost-ranked quick calls and 895
preserved careful calls, versus 1,649 quick calls for either older experiment.
The new quick calls perform 2,998,924 queries and record 40,765 useful emitted
matches. The preserved careful work is deliberately not included in those
quick-parser statistics. This is a combined-policy experiment, not an isolated
measurement of dual hashing or of gain ranking alone.

Timing remains noisy. For example, the new RGBA16 texture trials range from
1.511 to 2.093 seconds, while its baseline ranges from 1.868 to 2.095 seconds.
The PDF's Sparse time change is +7.12% here, unlike the earlier eight-file
run's -31.84%. Do not describe these aggregate percentages as guaranteed
speedups, or infer that MA itself became faster: no MA implementation changed.

## Decision

- Keep the three controls and the new combined candidate explicit and off by
  default. No Python, main CLI, effort mapping or production scheduler policy
  changes are justified by this sample.
- Sparse remains the better follow-up for a broadly conservative route: smaller
  total output and a lower observed total time than the cost-ranked combination.
  Its two individual size regressions still rule out a universal no-growth claim.
- Dual hashing is useful as a bounded candidate generator, but current seed
  decisions also influence fitted costs and admission to deep parsing. Cheaper
  matching is not equivalent to making the original deep search faster.
- The source seed's local gain is not the final ANS/table/context-map objective.
  Expanding spatial probes and preserving careful seeds recovered some size,
  but did not produce a stronger overall result than Sparse alone.
- Before any default-policy proposal, isolate careful preservation, spatial
  probing and gain ranking in separate ablations, then check the production
  scheduler on a larger corpus. Do not loosen the size tolerance or add
  filename-specific routing to force a win on this sample.
