# 多帧候选排序与开销复测

日期：2026-10-27。Windows x86-64，release DLL，e9，4 个原生线程。
本轮目标是减少已有候选的搜索开销，不增加候选、不降低 effort、不修改码流。
只采用小范围排序调整；不默认开启上一轮收益很小但代价大的多尺度搜索。

## 改动与被否决的方案

`multiframe/auto.rs::Candidate::estimated_work` 原先给 mask 的工作估计是
`changed_pixels + ceil(bbox_area / 64) + 64 * layers`。
mask 的零值内容确实可能很便宜，但仍需构造、转换和处理整个 bbox。
折扣过大会把昂贵 mask 排在更小的多矩形候选前，延迟建立有效的剪枝阈值。

首先试过完全按提交面积排序。t1 有改善，但一个离散稀疏变化的 RGBA 对照
从 4.412 秒变成 5.100 秒：原本会被快速剪掉的矩形候选反而先完整执行。
**这版没有采用。** 不能只看 t1 获益就认定排序正确。

保留的版本仍区分稀疏内容和 bbox 扫描，把上述 `/ 64` 调为 `/ 8`。
这是经验性执行成本权重，不是速度定律、压缩率估计或安全字节下界。
不新增统计扫描，也不删掉任何候选。真正剪枝仍只依据已确定输出的字节下界，
字节相同的选择仍按原规范顺序，不取决于谁先运行。

## 真实序列

使用 `strategy="auto"`、单一默认 32 网格、retained reference 和 lookahead，
与 [上一轮 base](MULTIFRAME_MULTISCALE_BENCHMARK.md) 配置一致。
旧 DLL 在本轮改动前复制保存，包含上一轮尚未提交的多帧增强；不是用 Git HEAD
重建的另一套实现。每次调用加载一个 DLL；新旧测试串行运行，不与编译或回归同时跑。

输入读取/初次解码和正确性比较不计入编码时间，Python 打包、FFI 和上下文计入。
bpp 和 MPix/s 分母使用全部完整逻辑画布像素，不用候选像素夸大吞吐量。
t2 比较 JPEG 解码后的同一份像素，不是 JPEG 文件字节可逆转码。

最后一组相邻运行 `before-3` / `final-2`：

| 输入 | 旧/新字节 | 旧/新 bpp | 旧编码秒 | 新编码秒 | 旧 MPix/s | 新 MPix/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| t1，4 x 4096 x 4096 RGBA | 12,478 / 12,478 | 0.001487 / 0.001487 | 19.606 | 18.246 | 3.423 | 3.678 |
| t2，4 x 2000 x 2183 RGB | 3,623,903 / 3,623,903 | 1.660056 / 1.660056 | 36.390 | 38.152 | 0.480 | 0.458 |

t1 此对照耗时降低约 6.94%，没有体积代价。t2 是无 mask 的 RGB 路径，排序键没有
改变，不能把它报告成提速；这一次实测反而慢约 4.84%。进程外系统负载/频率未固定，
没有足够证据声称该差异来自代码，也不据此声称所有输入都不会变慢。

为避免只展示最快的一次，本轮保留的重复结果如下，均为独立进程运行：

| 输入 | 旧版本编码秒，before-1/2/3 | 最终版本编码秒，final-1/2 |
| --- | --- | --- |
| t1 | 22.127, 16.768, 19.606 | 16.903, 18.246 |
| t2 | 41.572, 31.854, 36.390 | 38.173, 38.152 |

时间有明显波动，因此不宣称普遍固定百分比加速。更直接的执行证据是 t1 最后一帧：

- 原先先完成 `MaskFirst`：2,344 B、3.258 秒，再得到 991 B 的 `MergedFirst`。
  另一个 `MaskPrevious` 到 2,345 B 下界才被剪掉，耗时 3.932 秒。
- 新版先得到同一个 991 B 赢家，两个 mask 均在 992 B 下界终止，分别约
  2.339 和 2.248 秒。普通候选顺序和报告中的字节相等偏好没有改变。
- 整段完成候选数从 9 降为 8，剪枝数从 11 增为 12，候选总数仍为 20。
  `trial_pixels` 都为 104,529,920；它记录提交面积，不能表示一个已提交层内部
  有多少编码组在提前终止后未继续处理。

## Mask 反例检查

固定种子 19732 的 384 x 256 不透明 RGBA 随机背景，每组为原图、修改图、原图。
稀疏组修改两个远端像素并禁用多矩形；离散组每隔 13 像素修改一个位置；
密集组修改全部 RGB。每次修改为逐位 XOR，保持 alpha 不变。

| 对照 | 旧/新字节 | 旧秒，第一次/复测 | 最终新版秒 |
| --- | ---: | --- | ---: |
| 两点、禁用多矩形 | 322,559 / 322,559 | 4.452 / 4.727 | 4.471 |
| 大量离散变化 | 327,362 / 327,362 | 4.412 / 4.717 | 4.722 |
| 密集变化 | 645,087 / 645,087 | 5.367 / 5.897 | 6.028 |

最终版在三组上的完成/剪枝候选、赢家和层数均与旧版一致，避免了被否决版本
在离散组里额外完成整个矩形候选的问题。这些小样例不是自然图像吞吐量基准；
同样不能用单次计时差异宣称加速或绝对无退化。

## 采用边界

- 保留低成本排序修正，没有增加搜索或内存缓存规模。
- `extra_tile_sizes=[]` 仍为默认值，不用 2.30 倍时间去换 t2 额外的 0.833%。
- 这不是更强的帧间预测。当前样本的同位置差分边际收益已小，新的大幅体积收益
  需要不同的复用机会，例如滚动/平移的异位置精确块匹配；没有证据先不开重搜索。
- 当前选择仍以字节为准，不增加隐藏的耗时阈值，不用超时或低 effort 冒充优化。

解码后的全部原始样本验证通过；体积相同是本次不改变候选的预期检查，
不要求新旧 JXL 字节或哈希相同。原始报告在 `out/multiframe-order-e9/`：
`before-1/2/3`、`final-1/2`、`masks-before`、`masks-before-2`、`masks-final`。
`after-1/2` 与 `masks-after` 是被否决的纯面积排序实验，不能当作最终结果。

真实序列可用 `scripts/benchmark_multiframe_native.py <t1> <t2> --native <DLL>
--effort 9 --threads 4 --modes auto-lookahead --out <report.json>` 复测。
分析及判断方式见 [多帧分析指南](MULTIFRAME_ANALYSIS_GUIDE.md)。
